# Native switch recording: implementation checkpoint

The existing presence model permits multiple open `FRONTING` periods. Hosting is a separate kind, and `fronting_session` is a legacy single-front record. The legacy `switchCurrentFront` closes that record and starts another; using it as a substitute for reviewed changes to the current presence set would silently lose the multi-front semantics.

The native contract should read only the current open fronting episodes, then present the selected additions and endings with the current names before confirmation. The write should carry an immutable request ID, the selected active member IDs to start, and the exact episode IDs and versions to end. In one owner-locked transaction it must verify the reviewed current set has not changed, validate all members belong to the owner and are active, reject stale or duplicate selections, perform only those explicit changes, and store the receipt against the idempotency key. No timestamps supplied by a client and no automatic ending of other episodes. Expose only a separate narrowly scoped current-presence read and switch-write permission; no history, edit, delete, or MCP grant.

If a response is lost, preserve the immutable request and show an uncertain outcome until a receipt is retrieved or the exact request can be retried safely. An offline draft is not a recorded switch; it requires fresh online review before submission. Do not enable the new OAuth permission until the server contract, owner isolation, expired and wrong-audience handling, idempotency, race/conflict handling, and UI review are tested with mocks or disposable data.
